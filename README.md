# Remitlane

Remitlane is a cross-border payouts platform for African fintechs and marketplaces. Partners (our business
customers) call a REST API to quote and send payouts from a USD or NGN balance to bank accounts and mobile money
wallets in Nigeria (NGN), Kenya (KES), Ghana (GHS) and Uganda (UGX). We route each payout to a payout provider,
keep a double-entry ledger of every partner balance, and send signed webhooks back to the partner as the payout
moves. The operations and finance teams run the business from the ops console.

This README is for engineers joining the team. Partner-facing documentation is in [docs/api.md](docs/api.md) and
[docs/openapi.yaml](docs/openapi.yaml).

## Architecture

One Go binary (`cmd/remitlane`) serves the partner API (`/v1`), the server-rendered ops console (`/ops`), and the
provider webhook endpoints (`/webhooks/swiftpay`, `/webhooks/momobridge`), and runs the background worker and
scheduler in the same process. Postgres holds everything durable: partners, quotes, payouts, the ledger and webhook
history; most queries are generated by sqlc into `internal/db`, while list pages, reports and anything with optional
filters are hand-written in `internal/store`. Redis backs the asynq queues: payout dispatch, provider status polling,
partner webhook delivery with retries, the nightly reconciliation and balance alerts (`internal/jobs`). A payout is
priced from a quote (`internal/rates`, `internal/quotes`), booked with a ledger hold (`internal/payouts`,
`internal/ledger`), dispatched to Swiftpay (bank) or MoMoBridge (mobile money) by a job, and settled when the
provider's webhook arrives (`internal/inbound`); each status change writes a partner event that
`internal/outbound` delivers.

```
partner ──/v1──▶ api ──▶ payouts ──▶ ledger (Postgres)
                              │
                              └──▶ queue (Redis) ──▶ jobs ──▶ providers ──▶ Swiftpay / MoMoBridge
                                                       │                        │
partner ◀── signed webhook ── outbound ◀── payouts ◀── inbound ◀── provider webhook
```

| Path | What lives there |
| --- | --- |
| `cmd/remitlane` | entry point: `serve` (default), `migrate`, `seed`, `healthcheck` |
| `internal/api` | partner REST API, API key auth, idempotency keys |
| `internal/console` | ops console handlers, templates and static files |
| `internal/payouts` | create, bulk, dispatch, status transitions |
| `internal/rates`, `internal/quotes` | corridors, spreads, fees, quotes |
| `internal/ledger` | double-entry postings |
| `internal/providers/swiftpay`, `internal/providers/momobridge` | provider clients, status maps, webhook formats |
| `internal/providers/*/sandbox` | the local fake providers (see below) |
| `internal/inbound`, `internal/outbound` | provider webhooks in, partner webhooks out |
| `internal/jobs`, `internal/queue` | asynq handlers, scheduler, enqueue helpers |
| `internal/recon` | daily reconciliation report and CSV |
| `internal/store`, `internal/db` | hand-written SQL, sqlc output (do not edit `internal/db/*.go`) |
| `internal/devtools` | `/_dev` outbox and fake partner receiver |
| `internal/seed` | demo data loaded on start |
| `migrations` | goose migrations, numbered |

## Running it

### With Docker

```bash
docker compose up --build
```

The console is at http://localhost:5121 (it redirects to the login page). Compose starts Postgres 16 and Redis 7
without host ports, runs migrations and loads the demo data. Stopping and starting again gives you a fresh data set.

### Natively

You need Go 1.24, PostgreSQL 16 and Redis 7. The defaults expect Postgres on port 55421 and Redis on 56421 so they do
not clash with anything else you run; override with `DATABASE_URL` and `REDIS_ADDR`.

```bash
# once
initdb -D ~/.remitlane-pg -U postgres --auth=trust
pg_ctl -D ~/.remitlane-pg -o "-p 55421" -l ~/.remitlane-pg.log start
createdb -h localhost -p 55421 -U postgres remitlane
createdb -h localhost -p 55421 -U postgres remitlane_test

# each time
redis-server --port 56421 --save '' --daemonize yes
go run ./cmd/remitlane
```

Migrations run and the demo data reloads on every start (`MIGRATE_ON_START`, `SEED_ON_START`). `make migrate` and
`make seed` do either on its own.

## Money and time rules

- The API speaks integer minor units (`amount_minor`). NGN, KES and GHS have 2 decimals; **UGX has 0**, so
  `150000` UGX is one hundred and fifty thousand shillings. USD has 2.
- The ledger stores NUMERIC(20,4) major units. Every transaction's entries sum to zero per currency
  ([ADR 0002](docs/adr/0002-ledger.md)).
- A quote takes the corridor's spread off the mid-market rate and adds a flat fee in the source currency. The quote
  response shows `mid_rate`, `spread_bps` and the `rate` the partner gets. Spreads per corridor:

  | Corridor | Bank | Mobile money |
  | --- | --- | --- |
  | USD to NGN | 150 bps, fee $1.00 | n/a |
  | USD to KES | 120 bps, fee $1.50 | 100 bps, fee $0.75 |
  | USD to GHS | 150 bps, fee $1.50 | 120 bps, fee $0.75 |
  | USD to UGX | 200 bps, fee $2.00 | 150 bps, fee $1.00 |
  | NGN to NGN | no spread, fee NGN 50.00 | n/a |

- Quoting by source amount rounds the destination down; quoting by destination amount rounds the source up, so the
  recipient is never short. **KES mobile money is paid in whole shillings** (M-Pesa does not take cents), so those
  quotes round the destination down to the shilling.
- A quote is valid for 15 minutes (`QUOTE_TTL`) and can back one payout.
- Each partner has a **daily payout limit in USD**. Payouts in other currencies count at the mid rate; failed
  payouts do not count.
- **Business time is Africa/Lagos (WAT, UTC+1)** for daily limits, the reconciliation report and console dates,
  whatever zone the server or the partner is in. The daily limit resets at midnight Lagos time.

## Payout lifecycle

`pending` (booked, funds held) → `submitted`/`processing` (with the provider) → `completed` or `failed`. A completed
bank payout can later become `reversed` when the recipient's bank returns it; the amount and fee go back to the
partner. Failed payouts release the hold. Partners get `payout.processing`, `payout.completed`, `payout.failed` and
`payout.reversed` webhooks, signed with `Remitlane-Signature` (docs/api.md, Webhooks). Deliveries are retried
(`WEBHOOK_MAX_ATTEMPTS`); the ones that run out of attempts appear under **Failed webhooks** in the console, where
ops can retry one delivery or everything for a partner once the partner's endpoint is fixed.

If a provider webhook never arrives, the poller asks the provider about payouts that have not moved for
`POLL_STUCK_AFTER` (30 minutes). See [docs/runbooks/stuck-payouts.md](docs/runbooks/stuck-payouts.md).

## The fakes

Nothing here talks to a real provider or mail service. Each outside system has a local fake, picked by env:

| System | Env | Fake | What it does |
| --- | --- | --- | --- |
| Swiftpay | `SWIFTPAY_MODE=sandbox` | `internal/providers/swiftpay/sandbox` | v2 transfers API at `/_sandbox/swiftpay`; signed v2 (or v1) webhooks back to `/webhooks/swiftpay` after a delay |
| MoMoBridge | `MOMOBRIDGE_MODE=sandbox` | `internal/providers/momobridge/sandbox` | disbursements API at `/_sandbox/momobridge`; signed callbacks to `/webhooks/momobridge` |
| FX rates | `RATES_PROVIDER=fixed` | `internal/rates/feed.go` | fixed mid rates from `RATES_USD_*` |
| Email | `MAIL_PROVIDER=outbox` | `internal/mail` | messages land in `outbox_messages`, listed at **/_dev/outbox** |
| Partner endpoints | seed data | `internal/devtools/receiver.go` | **/_dev/receiver** records every webhook attempt and answers with each partner's configured status |

Sandbox magic values (account number or phone number endings that force an outcome) are in
[docs/sandbox.md](docs/sandbox.md). The console's **Sandbox** page lists what each fake received and can force the
next outcome.

## Tests and lint

```bash
go test ./...          # unit tests; database tests skip without DATABASE_URL
make test-db           # everything, against remitlane_test on localhost:55421
make lint              # golangci-lint v2 (.golangci.yml)
```

The store and payout service tests use the Postgres database in `DATABASE_URL` and truncate it, so point it at a
throwaway database. CI (`.github/workflows/ci.yml`) runs lint, the full test suite against a Postgres service, and a
Docker build on every pull request and on `main`.

## Changing queries

Edit `internal/db/queries/*.sql` (or add a migration in `migrations/`) and run `make sqlc` (sqlc 1.29). Commit the
generated files. Queries with optional filters go in `internal/store` instead.

## Configuration

Everything is an environment variable with a development default; see [.env.example](.env.example) for the full
list with comments. The ones you are most likely to touch:

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` / `APP_BASE_URL` | `5121` / `http://localhost:5121` | the base URL is where sandbox providers send webhooks |
| `DATABASE_URL` | `postgres://postgres@localhost:55421/remitlane` | |
| `REDIS_ADDR` | `localhost:56421` | |
| `SEED_ON_START` | `true` | wipes the database on start |
| `BUSINESS_TZ` | `Africa/Lagos` | |
| `SWIFTPAY_MODE`, `MOMOBRIDGE_MODE` | `sandbox` | `live` needs real credentials |
| `SWIFTPAY_API_VERSION` | `v2` | webhook format the Swiftpay sandbox sends |
| `WEBHOOK_MAX_ATTEMPTS`, `WEBHOOK_RETRY_BASE` | `5`, `2s` | partner webhook retries (linear backoff) |
| `DISPATCH_MAX_RETRY`, `DISPATCH_RETRY_BASE` | `3`, `2s` | provider dispatch retries (exponential) |
| `DEV_TOOLS_ENABLED` | `true` | mounts `/_dev` |

## Deploying

Production runs the Docker image (distroless, non-root) on our container platform with `SEED_ON_START=false`,
`DEV_TOOLS_ENABLED=false`, `CONSOLE_SECURE_COOKIES=true` and live provider credentials from the secret store. The
image embeds `time/tzdata`, so business-time logic works without zoneinfo files.
